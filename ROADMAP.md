# Roadmap

Statuses are `todo`, `in-progress`, `review`, `done` and `blocked` (with a reason). `done` means merged to main and accepted, not merely coded; the coordinator sets it after merge. Implementing any item needs an explicit assignment; a request to scaffold, document or plan is not one. Unbuilt features stay invisible in the dashboard and CLI until their item is done.

Each item is one PR on its own branch, built with the [wardlock-item](.agents/skills/wardlock-item/SKILL.md) skill once its dependencies are `done`. Workers change only their own item's Status and Owner fields (the coordinator records the PR when it marks the item `done`), then run `node scripts/roadmap-board.mjs` to refresh the board.

<details>
<summary>Branches, ownership and serialization gates</summary>

Each item is one focused PR on branch `feat/<id-lower>-<slug>`, implemented with the [wardlock-item](.agents/skills/wardlock-item/SKILL.md) skill; parallel lanes are coordinated with [wardlock-orchestrate](.agents/skills/wardlock-orchestrate/SKILL.md). Start an item only when every dependency is `done` on main. Workers update only their own item's Status and Owner fields. The **Parallel** line names the files an item owns, the serialization gates it touches (migrations and sqlc schema, `packages/api-spec`, `packages/ui`, `internal/access` cookie/session primitives, lockfiles) and the items it can share a wave with; check real file overlap before launching. One migration owner and one lockfile owner per wave.

</details>

### I6.3: Webhooks

- Status: `todo`
- Owner:
- PR:
- Depends on: I6.2, C1.19
- Scope: Owners register HTTPS endpoints that receive signed JSON events, for chat notifications and automation. Events: `deploy.activated`, `preview.deployed`, `preview.deleted`, `site.created`, `site.deleted`, `domain.status_changed`, `link.created`, `link.revoked`, `link.used_up` and `file.withheld`, plus `ping`. A webhook has a URL, a description, the events it wants (or all), an optional list of sites, and a signing secret shown once. Each delivery is a `POST` of `{id, type, created, data}` with `Wardlock-Event` and `Wardlock-Signature: t=<unix seconds>,v1=<hex HMAC-SHA-256 of "<t>.<body>">`; payloads carry names and IDs, never tokens, share-link secrets, visitor email addresses or file content. Deliveries use I6.2's outbox, retried with backoff for 24 hours after a non-2xx answer, a 10-second timeout or a connection error; a webhook failing for 3 days in a row is disabled and its owner emailed. SSRF defence: `https://` only (`http://` also in local mode); the dialler checks the address it actually connects to and refuses loopback, private, link-local, unique-local, multicast and unspecified addresses (operators can allow private ranges with `WARDLOCK_WEBHOOK_ALLOW_PRIVATE` for self-hosted chat servers); no redirects are followed; at most 4 KiB of a response is read. The last 50 deliveries per webhook are kept (status, duration, response code, no bodies) and any can be redelivered. API with the `manage` scope for changes; CLI: `wardlock webhook add URL [--event E]... [--site S]...`, `webhook list`, `webhook remove ID`, `webhook test ID` (sends a `ping`) and `webhook deliveries ID`. At most 10 webhooks per owner. A portable migration. Docs: SPEC (a "Webhooks" section with every event's payload and how to verify a signature, with Go and Node examples), SECURITY-MODEL (SSRF and signing) and the API contract. The dashboard is I6.4.
- Acceptance: Delivery tests against `httptest` servers for signing (checked by an independent implementation in the test), retries, backoff, disabling, redelivery and the 4 KiB cap; SSRF tests for each refused address class, a DNS answer that changes between lookups and a redirect; tests that no payload contains a secret; owner-isolation tests for every operation and that events from another owner's sites never reach a webhook; CLI tests against the fake server; store contract tests; generated code regenerated; `pnpm check` and `git diff --check` pass.

### T7.1: Teams, roles and isolation

- Status: `todo`
- Owner:
- PR:
- Depends on: C1.7, A2.13, A2.14, V5.3
- Scope: Add teams. A team has a name, members and sites; every site belongs to exactly one owner or one team, and personal sites stay. Roles: **admin** (members, roles, team settings and deleting the team, plus everything an editor can do), **editor** (everything an owner can do to a site today: deploys, policies, share links, custom domains, groups and tags, teardown) and **viewer** (reads only, including analytics and the access log). A team always keeps at least one admin. Members are existing owners, invited by email by an admin; an address with no owner account gets the normal owner invitation when `WARDLOCK_INVITES` allows it, and the invitation is refused otherwise. Leaving or being removed ends access at once, and what the member made stays with the team. Isolation becomes per actor: every owner-scoped repository method takes an `Actor` (the verified owner and their memberships, from the session or token, never the request) and allows a site that is the owner's or belongs to a team whose role permits the operation. Missing and foreign sites still answer the same `404`; `403 forbidden_role` is answered only where the actor can already see the site. Personal API tokens act as their owner, limited by both role and scope; team admins can create team tokens owned by the team, which survive members leaving (for CI) and are listed and revoked by the team's admins. Inviting and removing members stays dashboard-only, as owner invitations are. A team has its own groups and tags; pins stay personal. Owner quotas (A2.14) apply per team with their own overrides, and a team's deploys count to the team. Moving a site between an owner and a team, in either direction, needs admin on the team and ownership or admin of the source; it keeps deploys, links, domains and analytics, and is refused while the site is taken down. Deploys, policy changes, share links and domains record the member who made them (`createdBy` in the API). Operator controls (A2.13): suspending an owner ends their team access; taking down a team's site works as today; `wardlockd admin` lists teams and their members. API: teams, members, invitations, team tokens and site transfer; the Site object's owner becomes `{kind: owner | team, id, name}`. A portable migration that leaves every existing site with its current owner. Docs: SPEC (a "Teams" section; Teams removed from "Not in v1"), SECURITY-MODEL (the isolation rule, roles, team tokens), ARCHITECTURE, MODULES, AGENTS's owner-scoping rule, the isolation guidance in the `wardlock-access` and `wardlock-go-service` skills, and the API contract. The dashboard is T7.2 and the CLI T7.3.
- Acceptance: Owner-isolation tests as a matrix over every owner-scoped operation × {own site, a team site for each role, another team's site, another owner's site, after removal, a suspended member, a personal token, a team token with each scope}, each answering exactly as specified; tests that every existing operation behaves as before for an owner in no team; transfer and per-team quota tests; store contract tests for the migration; the full `wardlock-access` matrix; a security review of the diff recorded in the PR, as for A2.7; generated code regenerated; `pnpm check` and `git diff --check` pass.
