# Wardlock v0.3.0

The third alpha. The dashboard has been redesigned to stay easy to use with 50 or more sites. It adds an overview of what needs attention, groups, tags and pins, a sites map, and an analytics page that counts requests by day, site, way in, browser and (optionally) country. It also works on phones. It adds three database migrations, so back up before upgrading.

> **Still an alpha.** Everything in the [v0.1.0 warning](v0.1.0.md) still applies: no external security review, so not for anything sensitive; invite-only instances; a single server; and changes to come before v1. Report vulnerabilities privately as [SECURITY](../../SECURITY.md) describes, never in a public issue.

## What's new

| Change                   | What it does                                                                                                                                                               |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| New dashboard            | A rail (a bottom bar on phones), a sites navigator with saved views, groups and tags, and a jump-to palette (⌘K or Ctrl+K) on every signed-in page                         |
| Overview                 | The home page shows what needs attention (links expiring soon; quiet, untagged, public and taken-down sites), pinned sites, groups and live deploys                        |
| Groups, tags and pins    | Put each site in a group, give it up to 20 coloured tags and pin the ones you use most. Organise many sites at once, with undo. Edit groups, tags and notes on `/organise` |
| Sites list and map       | The sites list is built for many sites: sections, filters, search, compact rows on phones and bulk organising. `/sites?view=map` shows the same sites by group             |
| Site page tabs           | Each site has a header and Overview, Links, Access, Domains, Deploys, Access log and Settings tabs; on phones the access log is grouped by day                             |
| Analytics                | Requests over the last 7, 30 or 90 days for all sites, one site, a group or a tag: allowed and refused, by way in, top links and paths, and browsers                       |
| Requests by country      | Off by default. Name a free IP-to-country database in `WARDLOCK_COUNTRY_DB` to add a country to each access-log entry and a "Where requests come from" map                 |
| CLI: groups, tags, pins  | `wardlock group …`, `wardlock tag …`, `wardlock site organise …`, `wardlock pin` and `wardlock unpin`                                                                      |
| `pnpm demo` (developers) | A throwaway local server seeded with synthetic sites and 90 days of traffic, for looking at and screenshotting the dashboard                                               |

<details>
<summary>More detail on each change</summary>

- **The dashboard** ([SPEC "Dashboard"](../SPEC.md#dashboard-d31)). Every page uses the new design system in light and dark, and is laid out for desktop and phone widths. Each screen gets its sites from one owner-scoped summary read ([SPEC "Site summaries"](../SPEC.md#site-summaries-v55)), so it costs the same few database queries however many sites the owner has. The overview's expiring-links count leaves out links whose whole lifetime is an hour or less, such as the Open site button's 10-minute links.
- **Groups, tags and pins** ([SPEC "Groups, tags and pins"](../SPEC.md#groups-tags-and-pins-v53)). They belong to the owner alone. They change no policy, link or page a visitor sees. A site is in at most one group; an owner has up to 100 groups and 200 tags. One bulk request organises up to 500 sites, all or nothing. A deploy token can file the site it publishes; every other change needs a `manage` token.
- **Analytics** ([SPEC "Analytics"](../SPEC.md#analytics-v54)). It reads an hourly rollup of the access log. The rollup is written in the same transaction as each batch of log entries and kept 400 days by default (`WARDLOCK_ANALYTICS_RETENTION_DAYS`), so it outlasts the log itself. It holds no IP address, User-Agent, token or query string. Everything is counted as requests, never visits or visitors.
- **Countries** ([SPEC "Countries"](../SPEC.md#countries-v513), [DEPLOYMENT "Country lookup"](../DEPLOYMENT.md#country-lookup)). The lookup is local: no address is sent anywhere. It looks up the already truncated IP the log stores. While it is off, nothing records, reports or shows a country.
- **Dependencies.** Go and npm dependencies are updated, including `golang.org/x/net` v0.62.0, which fixes quadratic-time HTML parsing ([GO-2026-6860](https://pkg.go.dev/vuln/GO-2026-6860)) when a deployed page is converted to its Markdown and text renditions.
- **CLI** ([SPEC "CLI"](../SPEC.md#cli-c15-c17-c19-c114)). Groups and tags are named, not addressed by ID. Deleting either asks for confirmation and needs `--yes` without a terminal. `site organise` and `pin` change every named site or none.

</details>

## Upgrading from v0.2.0

1. Back up the database with `wardlockd backup` ([Backups](../DEPLOYMENT.md#backups)), or on the VPS deployment with `sudo systemctl start wardlock-backup.service`. Migrations `0012`–`0014` (groups, tags and pins; the traffic rollup; access-log countries) run on start and are forward-only, so going back to v0.2.0 needs the backup.
2. Replace the server binary or image and restart ([Upgrades](../DEPLOYMENT.md#upgrades)). On the VPS deployment, change the version to `0.3.0` in `compose.yaml` (or in `WARDLOCK_IMAGE` in `.env`) and run `sudo docker compose pull && sudo docker compose up -d` ([Upgrades on the VPS](../DEPLOYMENT.md#upgrades-on-the-vps)).
3. Upgrade the CLI with the same command you installed it with (below).
4. Optionally, turn on the country lookup ([Country lookup](../DEPLOYMENT.md#country-lookup)). Entries logged before it was on have no country.

<details>
<summary>The first start and mixing versions</summary>

On its first start, v0.3.0 counts the access log already stored into the analytics rollup, once, before it serves. On a large log this makes that start slower. Later starts skip it. Entries of sites that no longer exist are not counted.

The API only gained fields and endpoints, so a v0.2.0 CLI keeps working with a v0.3.0 server. A v0.3.0 CLI works with a v0.2.0 server except for the new `group`, `tag`, `site organise`, `pin` and `unpin` commands, which fail because the server lacks their endpoints. The dashboard is embedded in the server, so it always matches it. Upgrade the server first.

</details>

## Install

The four ways to install are unchanged from [v0.1.0](v0.1.0.md#install), with the new version:

```sh
curl -fsSLO https://raw.githubusercontent.com/CubieCode/wardlock/v0.3.0/deploy/install.sh
sh install.sh --version 0.3.0 --component all --dir ~/.local/bin   # wardlockd and wardlock, no root

WARDLOCK_IMAGE=ghcr.io/cubiecode/wardlock:0.3.0 docker compose -f deploy/compose.yaml up -d

go install wardlock.nz/cli/cmd/wardlock@v0.3.0
go install wardlock.nz/server/cmd/wardlockd@v0.3.0
```

<details>
<summary>Archives, the image and checking signatures</summary>

The GitHub release carries `wardlockd_0.3.0_<os>_<arch>` and `wardlock_0.3.0_<os>_<arch>` archives for Linux, macOS and Windows on amd64 and arm64, with `checksums.txt` and an SBOM per archive. `ghcr.io/cubiecode/wardlock:0.3.0` is the multi-arch (`linux/amd64`, `linux/arm64`) distroless image, which runs as a non-root user. Every archive, SBOM and the image carries a GitHub artefact attestation. To check one, run `gh attestation verify wardlockd_0.3.0_linux_amd64.tar.gz --repo CubieCode/wardlock` ([Verifying a release](../DEPLOYMENT.md#verifying-a-release)). Binaries built with `go install` report their version as `dev`.

</details>

## Known limitations

Unchanged from [v0.1.0](v0.1.0.md#known-limitations): no external security review, a single instance, deploy files in a bucket are not in `wardlockd backup`, basic abuse tooling and no key rotation.

## Reporting problems

- **Vulnerabilities:** report them privately, through the repository's **Security** tab ([SECURITY](../../SECURITY.md)). There is no bug bounty.
- **Bugs and questions:** open a GitHub issue on [CubieCode/wardlock](https://github.com/CubieCode/wardlock/issues), with the version (`wardlock version`), what you ran and what happened. Leave out tokens, share links, passwords and email addresses.
