# Wardlock v0.1.0

The first public alpha of Wardlock: a self-hostable static site host with access control built in. Deploy a folder to a subdomain with one command, then decide who can open it.

> **Alpha: read this first.**
>
> - Wardlock has **not had an external security review**. Do not use it to protect anything sensitive.
> - Instances are **invite-only**: there is no open sign-up, and abuse tooling for instances that let others deploy is still basic.
> - It runs as a **single instance**: one server, one SQLite database, no clustering.
> - **Expect changes before v1**, including to configuration and the API. Back up before every upgrade.
>
> Report vulnerabilities privately as [SECURITY](../../SECURITY.md) describes (the repository's **Security** tab, **Report a vulnerability**), never in a public issue. Other problems go in a GitHub issue.

## What Wardlock does

| Area                   | In v0.1.0                                                                                                                                                                                     |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Deploys and rollback   | `wardlock deploy ./dist docs` uploads only changed files and switches the site over atomically; every deploy stays in history and `wardlock rollback` brings back any earlier one instantly   |
| Share links            | A URL with a token (`?t=…`) that opens the page with no login screen; optional expiry, use limit, label and path scope; revoke or rotate at any time                                          |
| Policies               | Public, password, one-time email code and OAuth/OIDC (GitHub, Google or your own provider), with address, domain and organisation allowlists, per site or per path                            |
| AI-readable renditions | Share links work for `curl`, AI fetch tools and preview bots; every HTML page is also served as Markdown (`?format=md`) or plain text (`?format=txt`) behind the same access check            |
| Custom domains and TLS | Automatic certificates (wildcards through Cloudflare or deSEC DNS, on demand for custom domains) or a reverse proxy in front; owners verify a domain with one CNAME or TXT record             |
| Dashboard              | Sign in by email code or passkey; sites, deploy history and rollback, policies, share links, custom domains, Open site, and access logs per share link and per site                           |
| Long-term caching      | Opt in per deploy with `--immutable-assets` to cache hashed files under `/assets/` for a year                                                                                                 |
| Storage                | SQLite plus file bodies on disk, or in an S3-compatible bucket (AWS S3, Cloudflare R2, MinIO and others) with an optional local blob cache                                                    |
| Operations             | `/healthz`, an operator listener with `/readyz` and Prometheus `/metrics`, online backups with `wardlockd backup`, and a ready-made VPS deployment with automatic TLS, R2 and nightly backups |

The [SPEC](../SPEC.md) has every rule; [DEPLOYMENT](../DEPLOYMENT.md) has every setting.

<details>
<summary>More detail on each area</summary>

- **Deploys** ([SPEC "Deploys and rollback"](../SPEC.md#deploys-and-rollback-c12)). Default limits are 25 MiB per file, 10 MiB per video file, 20,000 files and 1 GiB per deploy, and 50 deploys of history per site. Garbage collection removes old deploys and unreferenced files hourly and with `wardlockd gc`. `--spa` turns on a single-page-app fallback per deploy.
- **Owners and the CLI** ([SPEC "Owners and sign-in"](../SPEC.md#owners-and-sign-in-c11-c16-c17)). Owners sign in to the dashboard with an emailed code or a passkey; there are no owner passwords. `wardlock login` approves the CLI in the browser and stores a scoped, revocable API token in the OS keychain; `WARDLOCK_TOKEN` serves CI.
- **Share links** ([SPEC "Share links"](../SPEC.md#share-links-a22)). Tokens carry 256 bits of secret, are shown once and stored only as HMACs. Use-limited links show an interstitial so preview bots and email scanners do not spend uses.
- **Policies** ([SPEC "Policies"](../SPEC.md#policies-a21)). Sites are public until their owner protects them. The longest matching path decides each request, and policies do not combine.
- **Custom domains** ([SPEC "Custom domains"](../SPEC.md#custom-domains-c19-d35)). A domain is served once DNS proves it and is re-checked daily; one whose record stays missing for 72 hours lapses and stops being served.
- **Access logs** ([SPEC "Access log"](../SPEC.md#access-log-a28)). Every request for a site's content records the time, path, status, how the visitor got in, the share link's label, a truncated IP and the User-Agent; never a token. Entries are kept 90 days by default.
- **Long-term caching** ([SPEC "Serving"](../SPEC.md#serving-c13)). Only deploys that opt in are affected. On a protected site the cached copies stay private to each visitor's browser, which keeps them for up to a year even after their access is revoked.
- **S3-compatible storage** ([DEPLOYMENT "S3-compatible blob storage"](../DEPLOYMENT.md#s3-compatible-blob-storage)). The database, rate limits and certificates stay on the machine, so this is still one server. The [blob cache](../DEPLOYMENT.md#blob-cache) keeps local copies of served files so the bucket sees few requests.

</details>

## Install

Pick one of the four ways below, then follow [first run](#first-run).

| Way              | Use it when                                         | Where the steps are                                                                  |
| ---------------- | --------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Release archives | You run `wardlockd` under systemd, or want the CLI  | [Install a release binary](../DEPLOYMENT.md#install-a-release-binary)                |
| Container image  | You run Docker or another container runtime         | [Docker](../DEPLOYMENT.md#docker)                                                    |
| VPS deployment   | You want one VPS with automatic TLS, R2 and backups | [VPS with automatic TLS and R2](../DEPLOYMENT.md#vps-with-automatic-tls-and-r2-o412) |
| `go install`     | You build from source with Go 1.27                  | Only once `wardlock.nz` serves its import paths; see [below](#go-install)            |

### Release archives

The GitHub release carries `wardlockd` and `wardlock` archives for Linux, macOS and Windows on amd64 and arm64, with `checksums.txt` and an SBOM per archive. [`deploy/install.sh`](../../deploy/install.sh) installs the right one for Linux or macOS, and refuses an archive whose checksum is missing or does not match:

```sh
curl -fsSLO https://raw.githubusercontent.com/CubieCode/wardlock/v0.1.0/deploy/install.sh
sh install.sh --version 0.1.0 --component all --dir ~/.local/bin   # wardlockd and wardlock, no root
```

<details>
<summary>Archive names, components and running under systemd</summary>

Archives are named `wardlockd_0.1.0_<os>_<arch>` and `wardlock_0.1.0_<os>_<arch>` (`.zip` on Windows, `.tar.gz` elsewhere); `checksums.txt` holds the SHA-256 of every archive and SBOM, and each SBOM is `<archive>.sbom.json` (SPDX). `--component` takes `wardlock` (the default), `wardlockd` or `all`. The `wardlockd` archive also contains `wardlockd.service`; [Single binary with systemd](../DEPLOYMENT.md#single-binary-with-systemd) installs it with the service user and environment file. The script never runs `sudo` itself. Windows is built but untested. Nothing is signed beyond the checksums.

</details>

### Container image

`ghcr.io/cubiecode/wardlock:0.1.0` is a multi-arch (`linux/amd64`, `linux/arm64`) distroless image that runs as a non-root user with data in the `/data` volume. [`deploy/compose.yaml`](../../deploy/compose.yaml) is an example:

```sh
export WARDLOCK_SECRET=$(openssl rand -base64 32 | tr '+/' '-_')   # keep a copy; see Backups
WARDLOCK_IMAGE=ghcr.io/cubiecode/wardlock:0.1.0 docker compose -f deploy/compose.yaml up -d
curl http://127.0.0.1:8080/healthz
```

### VPS deployment

[`deploy/vps/`](../../deploy/vps/README.md) runs `wardlockd` on one VPS with no reverse proxy: Wardlock obtains its own certificates through Cloudflare DNS, deploy files go to Cloudflare R2 with the blob cache in front, and a nightly restic backup goes to a second R2 bucket. Its `compose.yaml` already names `ghcr.io/cubiecode/wardlock:0.1.0`. Follow [VPS with automatic TLS and R2](../DEPLOYMENT.md#vps-with-automatic-tls-and-r2-o412) step by step; nothing is provisioned for you.

### go install

The Go modules use vanity import paths on `wardlock.nz` ([Go import paths](../DEPLOYMENT.md#go-import-paths)):

```sh
go install wardlock.nz/cli/cmd/wardlock@v0.1.0
go install wardlock.nz/server/cmd/wardlockd@v0.1.0
```

The release archives and building from a clone with `pnpm build` ([README "Quick start"](../../README.md#quick-start-development)) work too.

## First run

1. Generate a server key and keep a copy off the server: `openssl rand -base64 32 | tr '+/' '-_'`. It goes in `WARDLOCK_SECRET`.
2. Point a wildcard DNS record for sites and the dashboard host at the server, and choose who terminates TLS ([Quick start](../DEPLOYMENT.md#quick-start), [TLS](../DEPLOYMENT.md#tls)).
3. Configure [SMTP](../DEPLOYMENT.md#smtp), so sign-in and email codes reach people.
4. Start the server and open the one-time `setup_url` from its log to create the first owner. Invite further owners from the dashboard.
5. Turn on the [operator listener](../DEPLOYMENT.md#health-readiness-and-metrics) for `/readyz` and `/metrics`, and schedule [backups](../DEPLOYMENT.md#backups).

<details>
<summary>The setup URL and the alternative</summary>

The setup URL is valid for 60 minutes and once, and a new one is printed on every start until an owner exists: `journalctl -u wardlockd | grep setup_url` under systemd, `docker compose logs wardlockd | grep setup_url` under Docker. Instead, `wardlockd admin create --email you@example.com`, run with the server's environment, creates the owner and prints a one-time sign-in URL. Serve sites from a different registrable domain from the dashboard in production ([SECURITY-MODEL "Cookie tossing and cross-site session abuse"](../SECURITY-MODEL.md#cookie-tossing-and-cross-site-session-abuse)).

</details>

## Backups, upgrades and restore

- **Back up** the database with `wardlockd backup` (never copy the live file), then the deploy files, and keep `WARDLOCK_SECRET` safe separately: without it every share link, API token and session stops working after a restore. See [Backups](../DEPLOYMENT.md#backups), or [Backups and restore on the VPS](../DEPLOYMENT.md#backups-and-restore-on-the-vps).
- **Upgrade** by backing up, replacing the binary or image and restarting. Migrations run on start and are forward-only, so going back needs the backup. See [Upgrades](../DEPLOYMENT.md#upgrades) and [Upgrades on the VPS](../DEPLOYMENT.md#upgrades-on-the-vps).
- **Restore** into an empty data directory with the same `WARDLOCK_SECRET` and hosts. See [Restore](../DEPLOYMENT.md#restore).

## Known limitations

- **No external security review**, as above.
- **Single instance.** Rate limits, OAuth sign-ins in progress and passkey challenges live in memory: a restart resets the limiters early and drops sign-ins in flight, and several instances cannot share them.
- **Deploy files in a bucket are not in `wardlockd backup`.** It copies only the database; protect the bucket with versioning or replication ([Backups](../DEPLOYMENT.md#backups)).
- **Abuse tooling is basic.** Operators can suspend owners, take sites down, set owner quotas, limit video files, block file types and turn on optional content screening with OpenAI's moderation endpoint, and there is an acceptable use policy, but automated screening misses things and makes mistakes, so run an instance only for owners you trust ([SECURITY-MODEL "Public instances and abuse"](../SECURITY-MODEL.md#public-instances-and-abuse)).
- **No key rotation.** Changing `WARDLOCK_SECRET` ends every session and invalidates every share link and API token ([SECURITY-MODEL "The server key"](../SECURITY-MODEL.md#the-server-key)).
- **Not in v1:** teams and shared ownership, other database backends, multiple server instances and an MCP server ([SPEC "Not in v1"](../SPEC.md#not-in-v1)).

<details>
<summary>Risks the security model accepts</summary>

[SECURITY-MODEL](../SECURITY-MODEL.md) gives the reasoning for each:

- **Sharing a link with a tool shares the content.** AI providers and preview services may keep what they fetch; use expiring or use-limited links and revoke them when done. A site's own JavaScript can read the token before Wardlock strips it from the address bar, and clients without JavaScript keep the full URL ([Token leakage](../SECURITY-MODEL.md#token-leakage)).
- **A sign-in method can be held shut for one site.** Someone with six or more networks can keep a site's password, email-code, OAuth or share-link sign-in refused for as long as they keep going; they cannot get in, and visitors with a session are unaffected. Anyone who knows an allowed address can spend its email-code limits, and anyone who knows an owner's address can delay that owner's email sign-in for up to an hour; passkeys avoid the latter ([Brute force and enumeration](../SECURITY-MODEL.md#brute-force-and-enumeration)).
- **Revoking access does not remove what a browser already cached** from a deploy that opted into long-term caching ([Cookie tossing and cross-site session abuse](../SECURITY-MODEL.md#cookie-tossing-and-cross-site-session-abuse)).
- **A protected site cannot be embedded from another origin**, including one of its own custom domains loading assets from its `<name>.<base domain>` host.
- **A DNS record left behind can be claimed.** If an owner removes a custom domain but keeps its CNAME, whoever later holds that site name can claim the hostname ([Custom domain takeover](../SECURITY-MODEL.md#custom-domain-takeover)).
- **Hosted sites are not sanitised.** Containment is by origin isolation ([XSS from hosted sites](../SECURITY-MODEL.md#xss-from-hosted-sites)).
- **Out of scope for v1:** a malicious operator, hiding that a site exists (names travel in DNS, TLS SNI and certificate transparency logs), copy prevention once a visitor has access, and end-to-end encryption at rest ([Out of scope for v1](../SECURITY-MODEL.md#out-of-scope-for-v1)).

</details>

## Reporting problems

- **Vulnerabilities:** privately, through the repository's **Security** tab ([SECURITY](../../SECURITY.md)). There is no bug bounty.
- **Bugs and questions:** a GitHub issue on [CubieCode/wardlock](https://github.com/CubieCode/wardlock/issues), with the version (`wardlock version`), what you ran and what happened. Leave out tokens, share links, passwords and email addresses.
