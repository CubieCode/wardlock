# Wardlock v0.2.0

The second alpha. Several pages can now share one site without anyone holding a copy of the whole of it, any deploy's files can be downloaded again, and coding agents can publish pages with the `wardlock-publish` skill. It adds one database migration, so back up before upgrading.

> **Still an alpha.** Everything in the [v0.1.0 warning](v0.1.0.md) still applies: no external security review, so not for anything sensitive; invite-only instances; a single server; and changes to come before v1. Report vulnerabilities privately as [SECURITY](../../SECURITY.md) describes, never in a public issue.

## What's new

| Change                                | What it does                                                                                                                                                                                                                       |
| ------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Deploy into a path                    | `wardlock deploy ./mockup docs --path /mockup-x/` replaces only `/mockup-x/` and keeps the rest of the site live; an empty directory removes the path. The CLI, the API and the dashboard's deploy history show each deploy's path |
| Pull a site's files                   | `wardlock pull docs` downloads the files of the live deploy, or of any deploy in its history with `--deploy`, each checked against its SHA-256; `--path` pulls one path                                                            |
| `wardlock-publish` agent skill        | `npx skills add CubieCode/wardlock --skill wardlock-publish` lets a coding agent publish a page it generated privately under one of your sites and hand you a share link that opens only that page                                 |
| Listed sizes checked                  | A deploy that lists a file at a size other than the one the server stores is refused, instead of being served cut short                                                                                                            |
| Global flags before `policy set`      | `wardlock --json policy set …` and `wardlock --server URL policy set …` now work, like every other command                                                                                                                         |
| `wardlock pull` checks the site name  | When no directory is given, `pull` names it after the site and refuses a name from the server that is not a valid site name                                                                                                        |
| Path deploys refused by older servers | The v0.2.0 CLI refuses `deploy --path` against a v0.1.0 server, which would otherwise replace the whole site with the one path                                                                                                     |

<details>
<summary>More detail on each change</summary>

- **Path deploys** ([SPEC "Path deploys"](../SPEC.md#path-deploys-c113)). The server takes the site's live deploy as the base and makes a new deploy from the base's files outside the path plus the upload under it, so files outside the path are byte-for-byte unchanged. If another deploy goes live in the meantime, activation answers `409 stale_base` and the CLI retries once against the new version, so two path deploys made at once never drop each other's files. Limits and quotas count the whole merged deploy, and rollback works across path and full deploys. `"path"` in `wardlock.json` makes every deploy from that directory a path deploy, and `--path ''` overrides it. Removing a path asks you to type it on a terminal and needs `--yes` otherwise.
- **Pulling** ([SPEC "Pulling a deploy's files"](../SPEC.md#pulling-a-deploys-files-c114)). The API lists a deploy's files (`GET /api/v0/sites/{site}/deploys/{deployId}/files`) and downloads each body through that deploy, so a hash only another owner's deploy lists stays unreadable. Bodies come as attachments with `nosniff` and a restrictive CSP, so they never render on the dashboard's origin. `pull` refuses a directory that is not empty unless `--force` is given, writes each file under a temporary name until its hash matches, and retries network failures like `deploy`. A site the operator has taken down cannot be pulled (`409 site_unavailable`), and a file content screening withheld answers `451 file_withheld` and is skipped.
- **The agent skill** ([README "Agent skill"](../../README.md#agent-skill)). It publishes only to a protected root site, and for a new one deploys a placeholder and protects the site before deploying any content. It deploys each page into its own path, creates a share link scoped to that path, and lists, updates (pulling the live page first when the source is gone) and removes the pages it published. It needs the v0.2.0 CLI and server.
- **Listed sizes** ([SPEC "Deploys and rollback"](../SPEC.md#deploys-and-rollback-c12)). A file the owner already holds used to be accepted at any listed size, and the edge sent that size as `Content-Length`. Creating a deploy and activating it now both compare listed sizes with the stored files and answer `400 invalid_manifest`, naming the path and both sizes. Deploys created before v0.2.0 are not checked or repaired: they keep serving and rolling back as before, but a path deploy on a base that lists a wrong size is refused until a full deploy replaces it. None are known.

</details>

## Upgrading from v0.1.0

1. Back up the database with `wardlockd backup` ([Backups](../DEPLOYMENT.md#backups)), or on the VPS deployment with `sudo systemctl start wardlock-backup.service`. Migration `0011` runs on start and is forward-only, so going back to v0.1.0 needs the backup.
2. Replace the server binary or image and restart ([Upgrades](../DEPLOYMENT.md#upgrades)). On the VPS deployment, change the version to `0.2.0` in `compose.yaml` (or in `WARDLOCK_IMAGE` in `.env`) and run `sudo docker compose pull && sudo docker compose up -d` ([Upgrades on the VPS](../DEPLOYMENT.md#upgrades-on-the-vps)).
3. Upgrade the CLI with the same command you installed it with (below).

<details>
<summary>Mixing versions</summary>

The API only gained fields and endpoints, so a v0.1.0 CLI keeps working with a v0.2.0 server. A v0.2.0 CLI works with a v0.1.0 server except for the new commands: `deploy --path` stops with "does not support deploying into a path" before uploading anything, and `pull` fails because the server has no file listing. Upgrade the server first.

</details>

## Install

The four ways to install are unchanged from [v0.1.0](v0.1.0.md#install), with the new version:

```sh
curl -fsSLO https://raw.githubusercontent.com/CubieCode/wardlock/v0.2.0/deploy/install.sh
sh install.sh --version 0.2.0 --component all --dir ~/.local/bin   # wardlockd and wardlock, no root

WARDLOCK_IMAGE=ghcr.io/cubiecode/wardlock:0.2.0 docker compose -f deploy/compose.yaml up -d

go install wardlock.nz/cli/cmd/wardlock@v0.2.0
go install wardlock.nz/server/cmd/wardlockd@v0.2.0
```

<details>
<summary>Archives, the image and checking signatures</summary>

The GitHub release carries `wardlockd_0.2.0_<os>_<arch>` and `wardlock_0.2.0_<os>_<arch>` archives for Linux, macOS and Windows on amd64 and arm64, with `checksums.txt` and an SBOM per archive. `ghcr.io/cubiecode/wardlock:0.2.0` is the multi-arch (`linux/amd64`, `linux/arm64`) distroless image, running as a non-root user. Every archive, SBOM and the image carries a GitHub artefact attestation: `gh attestation verify wardlockd_0.2.0_linux_amd64.tar.gz --repo CubieCode/wardlock` ([Verifying a release](../DEPLOYMENT.md#verifying-a-release)). Binaries built with `go install` report their version as `dev`.

</details>

## Known limitations

Unchanged from [v0.1.0](v0.1.0.md#known-limitations): no external security review, a single instance, deploy files in a bucket are not in `wardlockd backup`, basic abuse tooling and no key rotation.

## Reporting problems

- **Vulnerabilities:** privately, through the repository's **Security** tab ([SECURITY](../../SECURITY.md)). There is no bug bounty.
- **Bugs and questions:** a GitHub issue on [CubieCode/wardlock](https://github.com/CubieCode/wardlock/issues), with the version (`wardlock version`), what you ran and what happened. Leave out tokens, share links, passwords and email addresses.
